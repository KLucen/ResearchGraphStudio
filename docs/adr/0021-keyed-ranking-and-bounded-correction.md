# ADR 0021：程序绑定的贡献评估槽位与有界格式修复

- 日期：2026-11-04 10:10（Asia/Shanghai）
- 状态：已接入；实际测试与交付结果见 [progress](../progress.md)
- 范围：P3/R5，不进入 P4 Query/P5 Lint/Wiki
- 运行版本：head 0011、领域 reading-extraction-1.0、入口 paper-reading-v1 不变

## 问题与责任

真实 P13v2 在两篇论文中反复输出重复、冲突或遗漏的结论编号，以及未知根字段。旧传输为 `ranked_claims` 数组，每项要求模型重复生成 `claim_ref`；精确覆盖与唯一性只能在生成后由 Python 检查，输出 Schema 没有固定本次允许的完整编号集合。整个列表同时承担身份抄写、语义判断和排序，局部格式失败便丢失整阶段进展，继续又可能重发相同的大请求。

用户要求软件解决协议可靠性，不应把更换模型当作修复前提。保留已发生的失败记录和费用事实，停止本轮新增付费调用；通过协议设计、确定性汇总与受限恢复降低这类失败，真实科学质量仍需独立验收。

## 新传输与程序职责

新建计划冻结 `P13_reading_ranking_v3`、`reading-ranking-keyed-1`。输出为 `assessments` 和 `warnings`，程序以请求内短编号生成固定对象属性，例如：

```json
{
  "assessments": {
    "c0001": {
      "recommendation": "suggest_core",
      "reasons": ["main_contribution"],
      "rationale": "基于所给原文的简短说明",
      "priority": 85
    }
  },
  "warnings": []
}
```

运行 Schema 把本次全部短编号列为 required properties，并在各层禁止额外字段；模型不再在列表项中生成编号，也不产生正式 ID、位置、成员或知识写入命令。建议、理由和说明直接复用领域 `SelectionHint` 的约束，`priority` 为严格整数 0–100。程序按优先级降序汇总，同分按冻结输入顺序稳定排列，不要求模型生成不重复的名次。分数是贡献排序辅助量，不是科学置信度。

静态 Prompt 的结构规则与同源模板 Schema 自动核对；每个请求另外携带由精确槽位 Schema 生成的规则和哈希。完整论文单元、原文、疑点、数字排版风险与密度上下文仍保留，不重新引入字符、候选或根数量预算。ADR0020 的证据感知检查和程序门槛继续生效。

## 部分结果与定向修复

严格 JSON 解析首先拒绝重复键（含转义后同名）、NaN/Infinity、未知根字段、未知短编号和不合法 warnings；这些响应不提取任何槽位。外壳合法时，各已知槽位独立通过严格 DTO 才能暂存；缺失或不合法槽位保留固定字段路径/错误类型诊断，不反射模型输入、未知字段名或任意错误消息。

一次新构建最多预留两个请求槽位：首次请求加一次格式修复。修复只要求未完成的输出槽位，仍提供完整论文上下文用于贡献、等价与条件比较；不让模型重写已通过槽位，不通过程序合并冲突建议、删除未知字段或猜测缺失值。原始响应始终保留，按槽位登记来源 ModelRun 与 raw SHA-256。部分结果只作为私有恢复材料，不是成功阶段或已发布图谱。

全部槽位齐备后，再绑定正式根 ID、文献版本、输入修订与已有缺口，经完整阶段终验和 KnowledgeStore 发布再验后才原子更新选择。首次失败预览及已有图保留继续遵循 ADR0017/0019/0020；任何格式修复都不能绕过证据与来源门槛。

## 请求账本与计费边界

持久账本冻结根输入哈希、请求序号、输入/Schema/manifest 哈希并在发送前预留槽位。恢复重新解析并验证已有响应，不信任历史状态或私有槽位缓存；已发送槽位不重发。所有发送（包括超时或投递状态不明）都占用上限，网络故障不在同一槽位内隐式重试；只有显式继续才可使用剩余槽位处理未完成工作。

达到上限报告 `RANKING_PROTOCOL_EXHAUSTED`，继续不再产生请求；界面显示输出已校验数、实际修复状态、上限及候选/旧图保留，不承诺再次继续就成功，也不要求更换模型。已有知识、历史响应和供应商未报告费用保留。来源、候选、关系或排版上下文发生变化时按可信输入冲突停止，不能靠额外调用修复。

## 旧任务兼容与独立续接

v1/v2 Prompt、Schema、冻结计划、签名、raw 和成功检查点均不改。旧 `selecting` 阶段失败且满足条件的任务，经原“继续未完成批次”入口创建独立 v3 后继任务；不原地改旧任务协议，也不重抽 P02。

后继仅在原候选快照、来源和支撑关系仍合法时创建。原 P12 的冻结输入与真实成功 ModelRun 必须重新经过完整来源/证据/DTO 校验和 Store 应用校验；保留原 ModelRun 作为谱系，不伪造新调用或复制成假成功记录。通过后零新 P12 请求采用原整合结果。缺少可核验检查点、历史响应不合法或支撑变化时明确停止，不悄悄转成一次新的付费 P12。

## 验收边界

离线覆盖：精确键 Schema、缺失/非法槽位、根/槽位未知字段、冲突重复键、非法 JSON、同分排序、局部修复、断点恢复、超时投递不明、两槽位费用上限、上下文变化、旧计划保持及 P12 零调用谱系；产品进度不把抽取批次完成当贡献评估完成。

本轮没有新增真实 API 调用。此前确认的 32 条语义无支持候选和 2 条上标误读仍是 R5 真实质量复验项；不能把新格式的离线通过当成已成功过滤这些内容。原生 strict、复杂解析、新包反馈及四份不可用外部原文分别记录。无数据库迁移、人工科学审核、Commit/Push 或下一 Phase 开发。
