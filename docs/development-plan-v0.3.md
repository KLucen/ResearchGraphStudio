# ResearchGraph Studio 开发流程方案

> 历史版本：由 2026-10-27 的原开发方案保留，正文不代表当前排期。后续新增范围与任务以[计划 v0.4](development-plan-v0.4.md)为准。

版本：v0.3；日期：2026-10-27。依据：[QA.md](../QA.md)、[需求基线](design/requirements-baseline.md)、[ADR 0002](decisions/0002-tauri-evidence-workbench.md)。本版替代 v0.2 的 Electron 暂案与 M0–M6 排期。

## 1. 开发目标与交付边界

开发方向确定为：**实验条件约束的跨论文证据推理 + 人工知识审核 + 持续知识演化**。工作台围绕论文中的具体主张和原文证据组织，不把论文摘要、语义相似度或关系图展示当作完整研究贡献。

首个 v0.1 版本完成：导入至少 5 篇相关论文 → 抽取主张与证据 → 比较实验条件 → 提出五类关系 → 人工确认/纠错 → 图谱查看 → 保存项目 → 导出报告。审核事件随首版保存，自动增量推理和完整版本回放留到 v1.0。

目标平台是 Windows 10/11 x64，目标工作区为约 10–30 篇英文计算机科学论文。先处理文本型 PDF；扫描件、复杂公式/图表/跨页表格显示解析限制，允许人工补充定位或修正，不能静默制造证据。模型未配置时，可打开已有项目、查看证据、编辑和导出；在线推理明确显示不可用原因。

v1.0 增加增量更新、Zotero 只读导入、实验评测中心和发布完善。自动搜论文、通用自主科研 Agent、全学科图谱、大型本地模型训练、双向 Obsidian 同步、多人协作不进入本次路线。

## 2. 三个工具的分工

| 工具/入口 | 职责 | 实现顺序 |
| --- | --- | --- |
| 直接 PDF 导入 | 独立完成从原文到证据的最短路径 | Phase 1，v0.1 必需 |
| ResearchGraph Studio | 主张/条件抽取、证据推理、审核、图谱、演化与实验 | 全阶段主线 |
| Zotero | 保存原始文献、题录和集合；本软件只读其 Local API | v0.1 预留来源模型，Phase 4 实现选择性导入与来源更新检查 |
| Obsidian | 人工精读笔记与写作；接收 Markdown/YAML frontmatter 导出 | Phase 3，保留引用和审核状态；用户选择目标，不自动双向同步 |
| MCP | 可选的未来外部 AI 工具接口 | 不作为 v0.1/v1.0 前置依赖 |

此顺序采用 QA 后半部分的四阶段与最终 MVP 描述，解决前面模块表将 Zotero 同步列为 P0 的范围差异。PDF 与 Zotero 适配器汇入同一个导入流程，保留外部标识、文件哈希和来源映射，避免同一附件产生两份知识。

## 3. 技术路线与目录

技术基线：Tauri 2 + React/TypeScript + React Flow；Conda Python 3.12 + FastAPI/Pydantic Sidecar；PyMuPDF；SQLite 关系表 + FTS5 + 向量候选召回。安装版携带打包引擎，开发环境依然使用 Anaconda。

```text
AI科研知识推理平台/
├── QA.md                         # 用户提供的设计原文，保留原貌
├── README.md / AGENTS.md / DEVELOPMENT_LOG.md
├── environment.yml / conda-win-64.lock
├── apps/
│   └── desktop/
│       ├── src/                  # 规划：React 三栏工作台
│       └── src-tauri/            # 规划：Rust 宿主、权限、Sidecar、打包
├── services/
│   └── engine/
│       ├── api/                  # 规划：受控业务接口、任务状态
│       ├── ingest/               # PDF 与 Zotero 来源适配
│       ├── extraction/           # 主张、条件、证据锚定
│       ├── reasoning/            # 候选召回、条件对比、五类关系
│       ├── evolution/            # 事件、影响分析、版本回放
│       ├── storage/              # SQLite、FTS5、迁移与事务
│       └── providers/            # 云端/本地模型接口
├── packages/contracts/           # 共享 schema 和生成的客户端类型
├── experiments/
│   ├── datasets/                 # 规划：来源/划分/标注清单
│   ├── baselines/                # 规划：三个实验的对照方法
│   └── evaluation/               # 规划：指标、原始结果与报告导出
├── tests/fixtures/               # 可分发的小型样本
├── docs/design/ + decisions/ + environment/
└── scripts/                      # 环境检查、后续构建/验证工具
```

保留当前源码根目录及 services/engine 路径，仅将旧 apps/web 占位职责归入 apps/desktop。引擎是单个本地程序，内部按模块划分；以上新模块目录在实现时建立，当前不是已实现代码。

Python 使用 `conda run -n researchgraph-studio ...`；依赖意图和 Windows 精确包分别维护在 environment.yml、conda-win-64.lock，pip-only 依赖另锁定。JS 使用 pnpm 锁文件，Rust 应用提交 Cargo.lock。根目录、Zotero 路径、GitHub origin 保持已确定配置。

## 4. 四阶段计划与验收关卡

采用 QA 细化版的约 10 周研究版计划，周数从 Phase 1 实现启动算起，不是日历交付承诺。假设单人、成熟模型 API、可获得样本文献；构建工具准备、标注和用户实验可能影响节奏。v0.1 预计在 Phase 3 结束交付。

| 阶段 | 时间 | 工作与交付 | 通过条件 |
| --- | --- | --- | --- |
| Phase 1：可安装论文导入器 | 第 1–2 周 | 补齐 Rust/MSVC；Tauri/React 壳、Conda 引擎、SQLite 迁移、PDF 导入/去重、页级原文与证据定位、初始安装包 | **M1 能安装**：干净 Windows 机无 Python/Node/Rust/Conda 前置，能创建项目、导入 PDF、查看证据；重启保存；退出无残留进程 |
| Phase 2：证据推理原型 | 第 3–4 周 | Pydantic 契约、主张/unknown 条件抽取、候选检索、条件对比、五类关系；最小审核 API/界面；记录模型配置和原始输出 | **M2 能推理**：至少 5 篇相关论文形成带来源候选关系；可人工纠错；无法定位证据的对象不能接受；缺证据案例输出 INSUFFICIENT |
| Phase 3：完整 v0.1 工作台 | 第 5–6 周 | 三栏证据审核、React Flow、关系编辑/撤回、项目持久化、事务性审核事件、报告/Markdown/JSON 导出、基础备份恢复 | 5 篇论文完整闭环通过；每条已接受实质关系可溯源；重启/导出不丢审核状态；交付 v0.1 安装版 |
| Phase 4：研究版 v1.0 | 第 7–10 周 | 增量影响分析、版本/差异/回放、Zotero 只读适配、实验中心、对比评测、完整安装/升级验证 | **M3 能演化**：新增文献只产生可审核变更且保留历史；**M4 能实验**：固定配置批量运行，导出预测、错误案例和报告；交付 v1.0 |

Phase 4 内部建议顺序：第 7 周增量算法与全量对照 → 第 8 周版本交互/Zotero → 第 9 周批量评估与用户实验 → 第 10 周复现、安装/升级、文档与演示。样本选择、标注规范和基线设计从 Phase 1 即开始，不到第 9 周才准备数据。

M1–M4 在本版表示 QA 的“安装、推理、演化、实验”四个关卡；开发日志中较早的 M0–M6 是历史暂案编号，不再用于新任务。

## 5. 第一轮可执行任务

以下均为待办，本轮仅更新规划。任务按依赖推进，不要求一次性安装全部框架。

| 任务 | 依赖 | 具体交付与验证 |
| --- | --- | --- |

| T102 最小桌面与 Sidecar | T101 | Tauri 启停 Python 服务，health/版本握手、受限命令、进程退出与错误显示；中文路径构建 |

## 6. 算法与数据开发顺序

实现顺序固定为：解析/证据锚定 → 结构化主张与条件 → 候选对召回 → 条件约束的五类推理 → 机器验证 → 人工接受 → 事件与物化状态 → 增量影响分析。

[领域模型](design/domain-model.md)定义核心表、证据定位、五类关系和六态审核流程。数据库读写统一由引擎执行；用户确认与相关事件在一个事务中写入。新证据不得静默覆盖已接受结论；修订需产生新版本并标记依赖关系复查。

阶段性算法结果必须能追踪到输入哈希、解析器/模型/提示词版本和原始输出。云端结果区分配置可追溯与输出完全确定复现，不能承诺后者总是成立。

## 7. 交互验收

左栏组织研究问题与论文；中栏为主张关系图；右栏同时展示双方证据、页码跳转、结构化条件差异、推理解释和审核操作。证据审查是主操作，聊天/摘要仅作辅助。

必须覆盖：空项目、处理中、损坏/扫描 PDF、引用不匹配、unknown 条件、INSUFFICIENT、模型未配置/超时、取消/重试、待审核、接受/拒绝/撤回。颜色之外还用文字和状态标识区分候选与已接受关系；INSUFFICIENT 不显示为已成立论证边。

v1.0 的演化视图回答新增/修改/撤回了什么、为什么变化、证据是什么、由谁确认；旧状态可回看，不只展示越来越大的图。

## 8. 验证与每轮工作流

1. 从需求编号与任务编号选一个可验收改动，先明确输入、失败场景和完成条件。
2. 变更数据或接口先更新契约/迁移；在对应独立环境实施小步改动，更新锁文件。
3. 验证实际风险：证据/去重/条件校验用固定样本，状态转换与事件用事务/重试用例；UI 经桌面、引擎、数据库到回显做端到端检查。
4. 安装验收覆盖无开发环境、中文/空格路径、WebView2 状态、离线使用、Sidecar 退出、升级保留数据及备份恢复。平台与版本逐项记录。
5. 研究效果执行[实验计划](../experiments/README.md)的 E1/E2/E3，保留失败和负结果。目标值不能记作实际结果。
6. 核对差异，更新需求/ADR/开发日志，写清执行了什么、结果与剩余问题。按任务需要提交和同步到已指定 origin；不上传个人论文、凭据或本机运行数据。

本轮已完成设计对照。下一项是 T101/T102 的构建与安装可行性验证，T103 的数据契约可在构建准备期间先行推进；不再等待分享链接恢复。
